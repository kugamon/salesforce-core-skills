Findings

Severity distribution

HIGH Failed-payment flow re-fires on every edit

"Internal Failed Payment Email" triggers on Create+Update of kugo2p__PaymentX__c with only status/amount filters and no ISCHANGED/ISNEW guard. Any edit to a payment already in Declined/Error/Failure (e.g. adding a note) sends a duplicate internal email and creates a duplicate task. Its sibling "Payment Received" flow has the correct guard — copy that pattern.

HIGH No fault paths anywhere (systemic, 5/5 flows)

Every fallible element across all five after-save flows — email alerts, quick actions, custom notification, record lookup, record create, and both async record updates — has faultConnector: null. In the three synchronous flows an action failure surfaces as CANNOT_EXECUTE_FLOW_TRIGGER against the user's save; in the two async close-date flows failures die silently. Add fault connectors (or an error-log subflow) to every fallible element.

MEDIUM Notification-type lookup without null check

"Internal Order Approved Email and Notification" gets CustomNotificationType "OrderApprovalNotification" by DeveloperName and feeds the Id straight into the notification action with no "record found?" decision. If the type is renamed or absent in a target org, the action fails at runtime.

MEDIUM Two async flows compete for Opportunity.CloseDate

The Primary Order and Primary Quote close-date flows both write Opportunity.CloseDate on async paths. When an Opportunity has both a primary quote and a primary order with different Date Required values, last-writer-wins is timing-dependent. Consider a precedence rule (order supersedes quote) in a single flow.

MEDIUM Report-export protection flow never activated

sfdc_default_ReportExport_Protection_Flow (Transaction Security) exists with no active version. If report-export monitoring is wanted, activate it; otherwise delete the draft to reduce noise.

MEDIUM Managed triggers + local flows on the same objects

Active kugo2p managed triggers exist on PaymentX, SalesOrder, SalesQuote, and Opportunity — the same objects the local flows fire on. This is expected for an ISV app and the package internals are not auditable, but order-of-execution interactions (e.g. package logic also touching CloseDate) should be verified in a sandbox before changing the flows.

LOW Dead "Create" path in both close-date flows

Both use trigger type Create+Update but include an IsChanged entry filter, which is false on insert — the Create half never fires. Harmless today (a brand-new primary order/quote won't sync the close date); switch to Update-only or restructure if create-time sync is intended.

LOW "− 0" no-op formula duplicated in two flows

OpportunityCloseDateCalculation is {!$Record.kugo2p__DateRequired__c} - 0 in both close-date flows — a leftover offset. Assign the field directly.

LOW Local Apex ageing at API v54

All 10 boilerplate classes and 2 flows sit at API v54 (4+ versions old). Low risk; batch-upgrade during the next maintenance window, or delete the site controllers if Experience Cloud is unused.

POSITIVE Clean modern-automation posture

No Workflow Rules, no Process Builders, no hardcoded Record IDs/URLs/Profile/Campaign names in any flow (the notification type is resolved by DeveloperName, not Id), correct PRIORVALUE/ISCHANGED guards in 4 of 5 flows, 1:1 test-class pairing on all local Apex, and zero custom triggers to maintain.

Top Recommendations (priority order)

  1. Add an ISCHANGED/ISNEW entry guard to "Internal Failed Payment Email" — stops duplicate internal emails/tasks today. (5-minute fix; copy the filter formula from the Payment Received flow.)
  2. Add fault connectors to all fallible elements in the three synchronous email flows so a mail/notification failure can never block a payment or order save.
  3. Add fault paths + an error-notification step to the two async close-date flows, and add a null-check decision after the CustomNotificationType lookup.
  4. Consolidate the two Opportunity close-date writers (or document quote-vs-order precedence) and remove the "−0" formula and dead Create paths while in there.
  5. Decide on the Transaction Security flow — activate report-export protection or delete the inactive default.
  6. Housekeeping: bulk-raise API versions (Apex v54 → current, flows v54 → current); remove unused site boilerplate controllers if Experience Cloud is not in use.
